# Self-Evolving OSINT-агент (LangGraph + ACE) — дизайн

**Дата:** 2026-08-11
**Источник требований:** `seminar/20-ai-agents/20-task.md`
**Артефакт:** `seminar/20-ai-agents/4_langgraph_ace_osint.py`

## Цель

Агент собирает досье на человека по открытым данным и **учится по ходу дела**: рефлексирует над качеством найденного и инкрементально дописывает собственный «плейбук» правил поиска, который использует на следующей итерации. Веса модели не меняются — меняется контекст.

Задание семинарское, тайминг 1.5 часа. Приоритет — наглядность эволюции правил, а не полнота OSINT.

## Принятые решения

| Решение | Выбор |
|---|---|
| Формат | Один скрипт-showcase в стиле `1_`–`3_` |
| Критерий остановки | Чек-лист слотов досье, не свободная оценка LLM |
| Персистентность | И Chroma, и playbook на диск |
| Цель поиска | Через `input()` с примером-подсказкой |
| Архитектура | 4 узла, инструменты только у Generator |
| Playbook | Операции ADD/REMOVE, лимит 7 правил |

## Состояние

```python
class AgentState(TypedDict):
    # пять полей строго из ТЗ
    target_person: str
    playbook: List[str]
    insights: str
    messages: Annotated[list, add_messages]
    iterations: int
    # расширения
    facts: Dict[str, str]   # выход Generator → вход RAG_Upsert
    missing: List[str]      # незакрытые слоты — вход Curator
    done: bool              # решение Reflector для условного ребра
```

Досье в state не хранится — оно живёт в Chroma. `rag_upsert` пишет, `reflector` читает через `query_profile`. Это единственное, что делает `query_profile` из ТЗ осмысленным, и держит state тонким.

**Слоты досье:** `role_title`, `organization`, `education`, `notable_work`, `online_presence`, `location`.

Шесть слотов подобраны так, чтобы первая итерация гарантированно не закрыла все — иначе эволюция playbook не будет видна.

## Топология

```
START → generator → rag_upsert → reflector ─┬─(done | iterations ≥ MAX_ITER)→ END
             ▲                              │
             └────────── curator ←──────────┘
```

Условное ребро одно, после `reflector`: `END`, если `missing` пуст **или** `iterations >= MAX_ITER` (по умолчанию 3); иначе `curator`. Ребро `curator → generator` безусловное.

`iterations` инкрементится в `generator` — в точке, где реально расходуются вызовы API.

Потолок в 3 итерации — из стоимости: каждая итерация это до 6 tool-call'ов Generator'а плюс три LLM-вызова, то есть один прогон ≈ 15–20 запросов к OpenAI.

## Инструменты

`exa_search` и `jina_reader` переносятся из `2_langchain_exa_search.py` — они проверены рабочим прогоном.

`Vector_DB_Manager` — две функции над коллекцией Chroma в `./chroma_osint` (с `persist_directory`):

- **`query_profile(name) -> dict[slot, str]`** — точное чтение по метаданным через `store.get(where={"name": name})`, не similarity search. Нужно досье конкретного человека, а не похожие документы.
- **`upsert_profile(name, facts: dict[slot, str])`** — id документа детерминированный: `f"{name}::{slot}"`, поэтому повторная запись слота перезаписывает, а не плодит дубли.

**Разрешение конфликтов** (без LLM): слот пуст → пишем; слот занят и новое значение не подстрока старого → дописываем через `; `, потолок 500 символов на слот.

Правило наивное и на длинных прогонах даст слоты вида «CEO; основатель; сооснователь». Принято сознательно: детерминированное и объяснимое поведение важнее аккуратности, LLM-мерж съел бы ещё один вызов на каждый слот.

Все три обёрнуты в `@tool`, но **LLM видит только `exa_search` и `jina_reader`**. Функции БД вызываются узлами напрямую через `.invoke()` — как `write_poem` в showcase 1. Права писать в базу у модели нет.

## Узлы

| Узел | LLM | Вход | Выход в state |
|---|---|---|---|
| `generator` | да, с 2 тулами | `target_person`, `playbook`, досье, `missing` | `messages`, `facts`, `iterations += 1` |
| `rag_upsert` | нет | `facts` | — (пишет в Chroma, логирует) |
| `reflector` | да, structured | досье из `query_profile` | `insights`, `missing`, `done` |
| `curator` | да, structured | `playbook`, `insights`, `missing` | `playbook` |

**Generator.** Системный промпт: цель + пронумерованный playbook + уже известные слоты + список недостающих. Внутри — цикл tool-calling с потолком 6 вызовов (как `ask()` в showcase 2). Финальный ответ структурированный: `{slot: value}`.

**RAG_Upsert.** Чистый Python, без LLM. Вызывает `upsert_profile`, печатает записанное.

**Reflector.** Структурированный выход `{missing: [...], insights: "..."}`. Решение о готовности принимает Python, а не модель: `decide_missing(dossier, reported)` объединяет слоты, реально пустые в Chroma, с теми, в которых усомнился Рефлектор. Модель может только **добавить** сомнение — объявить готовность при пустом слоте она не может.

Одного лишь `done = not missing` по ответу модели недостаточно: это переносит булев флаг, но не суждение. Хуже того, фильтр `if s in SLOTS` делал ложное «готово» проще — стоило модели ответить чужими именами слотов, как список опустошался и агент завершался с пустым досье на первой же итерации, ни разу не показав эволюцию playbook.

**Curator.** Возвращает **операции** `{add: [str], remove: [int]}`, а не новый playbook. Печатает диф (`+`/`-`) и полный playbook — это закрывает требование ТЗ «вывести `state['playbook']` на каждой итерации».

Порядок применения операций в Python:

1. **Удаления.** Индексы в `remove` — **1-based**, ровно те номера, которые Curator видел в пронумерованном playbook на входе. Python вычитает единицу и удаляет в порядке убывания индекса, чтобы не сдвинуть ещё не обработанные позиции. Индексы вне диапазона игнорируются.
2. **Добавления** — в конец списка.
3. **Усечение** до лимита 7: пока правил больше семи, выбрасывается самое старое **из добавленных Curator'ом**.

Два стартовых правила закреплены (pinned): они не вытесняются по лимиту, и попытка Curator'а удалить их игнорируется. Правила общие и остаются верными на любой цели; без закрепления они как самые старые вылетели бы первыми, и агент к третьей итерации забыл бы проверять однофамильцев.

**Стартовый playbook** (базовый, не пустой — ТЗ допускает оба варианта):

1. «Всегда добавляй к ФИО контекст специальности и города из запроса пользователя.»
2. «Проверяй, что найденная страница про нужного человека, а не однофамильца — сверяй специальность.»

Пустой старт сделал бы первую итерацию слепой и потратил бы её впустую при лимите в 3.

## Обработка ошибок

Первые два пункта — не гипотетические, мы на них наступили при прогоне showcase 2 в этой же папке.

- **Ошибка Exa.** Сейчас `r.json().get("results", [])` молча возвращает `[]` при 401, и агент остаётся без URL, не понимая причины. Новый инструмент проверяет статус и возвращает LLM строку `{"error": "..."}`. Побочная польза для ACE: Reflector видит отказ инструмента и может превратить его в правило.
- **Нет ключей.** Падение на старте с внятным сообщением, а не через три LLM-вызова. `OPENAI_API_KEY` требуется всегда, включая `--offline`; `EXA_API_KEY` — только в живом режиме.
- **Jina.** Таймаут или не-200 → маркер ошибки вместо пустой строки; обрезка до 4000 символов.
- **Структурированный вывод.** Через `.with_structured_output()`, а не ручной `json.loads` по срезу `{...}` как в showcase 1 — тот срез ломается на любом markdown-фенсе.
- **Зацикливание.** Основной ограничитель — `MAX_ITER`. Дополнительно `recursion_limit=25` при `invoke`: в showcase 1 его нет, и при упрямом Reflector граф падает вместо остановки.

## Проверка

Формат — один скрипт без pytest-слоя, поэтому проверок две.

**`--selftest`** — встроенные проверки чистых функций и хранилища. Вот они действительно не ходят в сеть: эмбеддинги подменяются на `DeterministicFakeEmbedding`, ключи не нужны.

**`--offline`** — подменяет фикстурами **только Exa и Jina** (ТЗ прямо разрешает «или замокать»). Четыре узла графа всё равно зовут OpenAI, так что ключ `OPENAI_API_KEY` нужен и прогон занимает минуты, а не секунды. Это страховка от исчерпанной квоты Exa, а не автономный режим.

Из-за фейковых эмбеддингов офлайн-данные лежат в **отдельной** коллекции `./chroma_osint_offline`. Коллекция Chroma имеет фиксированную размерность (64 у фейковых, 1536 у настоящих), и общая директория означала бы падение на `add_texts` при первом же переключении режима — причём уже после того, как Generator потратил вызовы LLM.

Критерии готовности:

1. playbook печатается на каждой итерации и **между итерациями отличается**;
2. `missing` сокращается от итерации к итерации;
3. на цели с распространённым именем и узкой специальностью агент делает ≥2 итерации; на простой выходит раньше по `done`;
4. повторный запуск с тем же именем видит досье в Chroma — доказательство персистентности.

## CLI и файлы

Цель запрашивается через `input()` с примером в подсказке. Флаги: `--reset` (снести `chroma_osint/` и `playbook.json`), `--offline`, `--max-iter N`.

`--reset` нужен потому, что playbook персистентный: без сброса второй прогон стартует с готовыми правилами и эволюции не покажет.

## Что осознанно не делается

- Мерж слотов через LLM — дорого, недетерминированно.
- Инструменты у Reflector и Curator — роли расплываются, Reflector начинает искать вместо критики.
- `create_react_agent` вместо явного `StateGraph` — не закрывает пункт чек-листа ТЗ про условные рёбра.
- Ранжирование правил playbook по эффективности — вытеснение по возрасту достаточно для демо.
